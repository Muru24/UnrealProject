# 코드 구조 및 리팩토링 가이드

## 목적

이 문서는 현재 프로젝트 코드의 역할 분담, 주요 흐름, 리팩토링 필요 지점을 한글로 정리한 1차 가이드입니다.

이번 정리는 다음 범위에 집중합니다.

- 플레이어 루트 구조
- 레일 이동 구조
- 편대/기체 구조
- 발사 책임 분리 상태

## 현재 구조 요약

### 1. 플레이어 루트: `AP_Player`

`AP_Player`는 현재 프로젝트의 플레이어 루트 Pawn입니다.

현재 책임:

- 입력 수신
- 카메라 제어
- 레일 이동 최종 적용
- 편대 스폰 및 활성 슬롯 갱신
- 메인 발사/서브 자동 사격 흐름 호출

현재 붙어 있는 핵심 컴포넌트:

- `ULockOnComponent`
- `UPathFollowerComponent`
- `URailOffsetComponent`
- `USquadComponent`
- `USquadRuntimeComponent`
- `UPlayerAimFireComponent`
- `UPlayerCameraRigComponent`
- `UPlayerRailMovementComponent`
- `USupportFireComponent`

현재 평가는 다음과 같습니다.

- 이전보다 책임이 줄었지만 아직도 조정자 역할이 크다.
- 편대 스폰/보관 책임은 `USquadRuntimeComponent`로 분리되었다.
- 카메라 팬/활성 기체 추적은 `UPlayerCameraRigComponent`로 분리되었다.
- 레일 최종 합성도 `UPlayerRailMovementComponent`로 분리되었다.
- 그래도 발사 판단 책임은 이미 컴포넌트로 분리되었기 때문에 방향은 좋다.

### 2. 레일 이동: `UPathFollowerComponent` + `URailOffsetComponent`

현재 이동은 두 레이어로 나뉩니다.

- `UPathFollowerComponent`
  - 스플라인을 따라 전진
  - 기본 월드 트랜스폼 계산
  - 가속/감속 반영
- `URailOffsetComponent`
  - 상하좌우 입력 기반 로컬 오프셋 계산
  - 복귀 보간
  - 메쉬 시각 기울기 계산

최종 적용은 `AP_Player::ApplyRailMovement()`에서 처리합니다.

현재 평가는 다음과 같습니다.

- 역할 분리는 비교적 잘 되어 있다.
- 다만 `UPathFollowerComponent` 내부 주석과 변수명이 일부 정리되지 않았다.
- `InterpSec` 같은 값은 기본값과 0 보호 로직이 필요하다.

### 3. 편대 구조: `USquadComponent` + `ASquadCraftActor`

편대는 플레이어 루트에 붙는 별도 기체 액터 3기로 구성됩니다.

- `USquadComponent`
  - 활성 슬롯 관리
  - 슬롯 오프셋 제공
- `ASquadCraftActor`
  - 개별 기체 표현
  - 메쉬/파이어 오리진 보유
  - 공격/로드아웃/스킬 컴포넌트 소유

현재 평가는 다음과 같습니다.

- 편대 자체는 Has-a 구조로 잘 분리되었다.
- 각 기체를 독립 액터로 둔 선택은 이후 HP, 피격, 역할 차별화에 유리하다.
- 다만 `ASquadCraftActor`는 앞으로 기체 비주얼, 피격 반응, 스킬 연출까지 커질 수 있으니 역할 확장 시 주의가 필요하다.

### 4. 발사 구조: 메인/서브 분리

현재 발사 책임은 다음처럼 나뉩니다.

- `UPlayerAimFireComponent`
  - 메인 기체 조준 발사
  - 록온 중이면 록온 대상 기준
  - 아니면 마우스 조준 기준
- `USupportFireComponent`
  - 서브 기체 자동 사격
  - `CombatRole` 기준으로 타겟 선택 차등 처리

현재 평가는 다음과 같습니다.

- `AP_Player`에 있던 발사 판단이 빠져서 구조가 좋아졌다.
- 이후 보스 약점/마커 시스템이 들어오면 이 두 컴포넌트가 가장 먼저 확장될 가능성이 높다.

### 5. 기체 설정 구조: `UCraftLoadoutComponent`

현재 기체별 공격 성격은 `LoadoutData`에 모여 있습니다.

대표 값:

- `Identity`
- `AttackConfig`
- `SkillConfig`
- `PresentationConfig`

현재 평가는 다음과 같습니다.

- 기체 설정이 한 곳에 모여 있다는 점은 매우 좋다.
- 공격/스킬/표현 설정이 별도 묶음으로 나뉘면 BP 작성과 확장이 더 쉬워진다.
- 앞으로는 `BP_SquadCraft_*`에서 공격 관련 값은 `LoadoutData`만 만지는 규칙을 유지해야 한다.

## 1차 리팩토링 필요 지점

### 우선순위 높음

1. `UPathFollowerComponent` 변수/주석 정리
- 깨진 주석 제거
- `InterpSec` 기본값 및 0 방어 필요

2. `AP_Player` 내부 카메라/편대 갱신 흐름 정리
- `ApplyRailMovement()`
- `UpdateCameraAnchor()`
- `RefreshSquadCrafts()`
세 함수가 현재 플레이어 상태를 강하게 묶고 있다.

3. 편대 스폰 로직 주석 보강
- `SpawnSquadCrafts()`는 현재 꽤 중요한 초기화 함수인데 읽는 사람이 구조를 빠르게 이해하기 어렵다.

### 우선순위 중간

1. `ASquadCraftActor`에 피격/비주얼 반응 확장 포인트 주석 추가
2. `LoadoutComponent`와 `SkillComponent`의 관계 문서화 보강
3. `SupportFireComponent` 타겟 선택 정책을 enum 기반으로 확장 가능하게 준비

## 현재 컴포넌트별 역할 정리

### `ULockOnComponent`

- 현재 대상 탐색
- 록온 on/off
- 대상 변경

### `UPathFollowerComponent`

- 스플라인 전진
- 기본 위치/회전 계산
- 속도 및 가속 처리

### `URailOffsetComponent`

- 플레이어 입력 기반 XY 이동 오프셋
- 기체 시각 기울기 계산

### `USquadComponent`

- 활성 슬롯 관리
- 슬롯 위치 오프셋 계산

### `USquadRuntimeComponent`

- 편대 기체 스폰
- 슬롯별 기체 참조 보관
- 활성 상태/목표 상대 트랜스폼 갱신

### `UPlayerAimFireComponent`

- 메인 기체 조준 결정
- 실제 메인 발사 요청

### `UPlayerCameraRigComponent`

- 마우스 기반 카메라 팬
- 활성 기체 기준 카메라 앵커 추적

### `UPlayerRailMovementComponent`

- `PathFollower`와 `RailOffset` 결과 조합
- 플레이어 최종 위치/회전 반영
- 활성 편대 기체 시각 기울기 반영

### `USupportFireComponent`

- 서브 기체 자동 사격 여부 판단
- 역할별 타겟 선택

### `UCraftAttackComponent`

- 총알 스폰 실행
- 단발/버스트/스프레드 실행
- 자동사격 쿨다운 유지

### `UCraftLoadoutComponent`

- 기체 전투 설정 데이터 보관
- 공격/스킬 컴포넌트에 설정 적용

### `USkillComponent`

- 스킬 슬롯 보관
- 쿨다운 관리
- 버프/공격 스킬 발동 진입점 제공

## 참고

- `AttackComponent`는 런타임 실행기
- `SquadCraftActor`는 비주얼/개별 기체 단위
- `AP_Player`는 루트 조정자

## 2차 정리: 타겟팅과 발사 판단

### 범위

이번 정리 대상:

- `ULockOnComponent`
- `UPlayerAimFireComponent`
- `USupportFireComponent`

### `ULockOnComponent`

현재 역할:

- 락온 on/off 상태 관리
- 현재 타겟과 타겟 인덱스 유지
- 가장 가까운 적 선택
- 다음 타겟 순환

리팩토링 필요 포인트:

1. 적 목록 접근 코드가 내부에 반복되어 있었다.
2. 타겟 인덱스 계산이 섬세하지 않아 잘못된 인덱스를 잡을 가능성이 있었다.
3. 락온 해제 시 타겟 정리 흐름이 명시적이지 않았다.

2차 정리 방향:

- 적 목록 접근을 helper로 분리
- 타겟 클리어 함수 분리
- 타겟 인덱스 계산 안정화
- 외부 시스템은 공개 필드 대신 getter를 통해 상태를 읽도록 정리

### `UPlayerAimFireComponent`

현재 역할:

- 활성 기체 발사 진입점 제공
- 락온 기반 조준과 마우스 기반 조준 분기
- 최종적으로 활성 기체에게 발사 요청

현재 평가는 다음과 같다.

- 책임이 명확하고 크기도 적당하다.
- 이후 보스 약점/저지 마커 시스템이 들어오면 가장 먼저 확장될 지점이다.
- 지금은 입력 처리와 발사 판단 사이의 연결 컴포넌트로 충분히 적절하다.

향후 확장 포인트:

- 보스 약점 우선 조준
- 락온 시 화면 보정
- 무기별 조준 규칙 차별화

### `USupportFireComponent`

현재 역할:

- 비활성 기체 자동 사격 여부 판단
- 역할별 타겟 선택
- 실제 자동 사격 호출

현재 평가는 다음과 같다.

- `AP_Player`에서 자동 사격 판단이 빠져나와 구조가 개선되었다.
- 다만 현재는 "가장 가까운 적"과 "락온 대상" 수준이라 이후 우선순위 계층이 필요하다.

리팩토링 필요 포인트:

1. 사용하지 않는 인자는 제거하는 것이 좋다.
2. 타겟 선택 정책을 나중에 enum 또는 정책 객체로 확장할 여지가 있다.
3. 약점/마커 시스템 도입 전까지는 현재 구조로 충분하다.

### 현재 결론

타겟팅/발사 판단 계층은 현재 다음처럼 정리된다.

- `ULockOnComponent`
  - 현재 수동 락온 상태 보관
- `UPlayerAimFireComponent`
  - 메인 기체 발사 조준 결정
- `USupportFireComponent`
  - 서브 기체 자동 사격 판단 및 타겟 선택

즉 플레이어 루트인 `AP_Player`는 이제 발사 로직을 직접 계산하기보다,
각 책임 컴포넌트를 호출하는 조정자 역할에 더 가까워졌다.

## 3차 정리: 공격 실행과 로드아웃 적용

### 범위

이번 정리 대상:

- `UCraftAttackComponent`
- `ABulletBase`
- `UCraftLoadoutComponent`

### `UCraftAttackComponent`

현재 역할:

- 기체 공격 실행 진입점
- 단발/버스트/스프레드 패턴 분기
- 발사체 스폰
- 자동 사격 쿨다운 유지

현재 평가는 다음과 같다.

- 실제 발사 실행기 역할이 분명하다.
- `LoadoutData`에서 넘어온 설정을 소비하는 구조라서 BP 작성 규칙과 잘 맞는다.
- 다만 공격 설정 타입 정의를 가져오기 위해 `CraftLoadoutComponent`와 직접 연결되어 있어 계층 결합이 약간 남아 있다.

리팩토링 필요 포인트:

1. 조준 회전 계산이 패턴 함수에 반복되지 않게 유지하는 것이 좋다.
2. 로드아웃에서 들어오는 수치는 런타임에서도 한 번 정규화하는 편이 안전하다.
3. 장기적으로는 공격 패턴 enum과 공격 설정 구조를 별도 타입 헤더로 분리하면 결합을 더 줄일 수 있다.

현재 결론:

- 지금 단계에서는 `UCraftAttackComponent`를 그대로 실행기 중심으로 유지하는 것이 맞다.
- 대신 설정 데이터 정의는 나중에 `CraftCombatTypes` 같은 공용 타입 파일로 분리할 가치가 있다.

### `ABulletBase`

현재 역할:

- 총알 수명 관리
- 충돌/오버랩 진입 처리
- 대상 데미지 적용
- 관통/폭발/비관통 규칙 실행
- 히트 이펙트 재생

현재 평가는 다음과 같다.

- 공격 타입별 실제 규칙은 한 곳에 모여 있어 읽기 좋다.
- `DamagedActors`를 통해 관통/폭발 중복 타격을 막는 방식도 현재 요구에 잘 맞는다.
- 반면 `TargetActor`와 `SetTarget()`은 현재 직진탄 구조에서는 쓰이지 않고 남아 있다.
- 헤더 쪽 깨진 주석과 오래된 표현은 아직 정리 대상이다.

리팩토링 필요 포인트:

1. 현재 사용하지 않는 유도 관련 인터페이스는 향후 계획을 확인한 뒤 정리 여부를 결정하는 것이 좋다.
2. 총알 이동, 충돌, 데미지 규칙이 계속 커지면 `Movement`와 `Impact` 책임을 분리할 필요가 생길 수 있다.
3. 폭발 범위 판정은 지금은 충분하지만, 나중에 팀 판정이나 약점 판정이 들어오면 별도 전투 규칙 계층이 필요할 수 있다.

현재 결론:

- 지금은 `ABulletBase` 하나로 유지해도 충분하다.
- 다만 기능이 더 늘기 전에 "직진탄 공통 베이스"와 "특수 규칙 확장"의 경계를 계속 의식하는 편이 좋다.

### `UCraftLoadoutComponent`

현재 역할:

- 기체 전투 설정 저장
- 공격 컴포넌트와 스킬 컴포넌트에 설정 주입
- 기체 역할 조회 창구 제공

현재 평가는 다음과 같다.

- BP 편집 창구를 한 곳으로 모아 둔 점이 가장 큰 장점이다.
- `AttackComponent`와 `SkillComponent`를 직접 실행하지 않고 설정만 전달하는 점도 역할 분리가 좋다.
- 현재 구조는 단순하고 안정적이지만, 장기적으로는 데이터 자산 기반 로드아웃으로 커질 가능성이 있다.

리팩토링 필요 포인트:

1. 빈 라이프사이클 훅은 유지하지 않는 편이 좋다.
2. 로드아웃 필드가 계속 늘어나면 `공격 설정`, `스킬 설정`, `표현 설정`처럼 묶음을 나누는 것을 고려할 수 있다.
3. 이후 기체 수가 많아지면 `DataAsset` 기반 외부 정의로 옮기는 것도 자연스럽다.

현재 결론:

- 현 단계에서는 `UCraftLoadoutComponent`가 BP 작성 기준점 역할을 잘 수행하고 있다.
- 지금은 컴포넌트 유지가 맞고, 데이터 양이 더 커질 때 구조를 한 단계 더 분리하면 된다.

### 이번 정리 반영 사항

- `UCraftAttackComponent` 내부에서 조준 회전 계산을 helper로 통일
- `UCraftAttackComponent`가 로드아웃 값을 적용할 때 런타임 기준으로 한 번 더 보정
- `UCraftLoadoutComponent`의 빈 `BeginPlay()` 제거

### 현재 계층 결론

전투 실행 계층은 현재 다음처럼 보는 것이 가장 명확하다.

- `UCraftLoadoutComponent`
  - 무엇을 쏘고 어떤 규칙을 쓸지 정의
- `UCraftAttackComponent`
  - 언제 어떻게 총알을 생성할지 실행
- `ABulletBase`
  - 생성된 총알이 실제로 어떤 판정과 결과를 낼지 처리

즉 로드아웃은 설정, 어택 컴포넌트는 실행, 총알은 결과 처리라는 3단 분리가 현재 구조의 핵심이다.

## 4차 정리: 스킬 골격과 스킬 데이터

### 범위

이번 정리 대상:

- `USkillComponent`
- `USkillEffectBase`
- `FSkillSpec`
- `ESkillType`

### `USkillComponent`

현재 역할:

- 버프 스킬과 공격 스킬 슬롯 보관
- 슬롯별 쿨다운 감소
- 실제 스킬 발동 진입점 제공
- 로드아웃에서 넘어온 스킬 스펙 적용

현재 평가는 다음과 같다.

- 지금 구조는 "스킬 관리자" 역할로 분명하다.
- 실제 효과 구현을 내부에 넣지 않고 `USkillEffectBase`에 위임하는 점이 좋다.
- 반면 현재는 버프 슬롯과 공격 슬롯이 고정 2칸이라, 나중에 일반 슬롯 기반 구조로 확장할 가능성은 남아 있다.

리팩토링 필요 포인트:

1. 로드아웃에서 받아온 스킬 스펙은 컴포넌트 내부에서 한 번 더 보정하는 편이 안전하다.
2. 현재는 쿨다운 두 개를 직접 들고 있으므로, 장기적으로는 슬롯 구조체로 묶는 방식도 고려할 수 있다.
3. 자동 발동, 입력 발동, 보스 전용 발동처럼 호출 주체가 늘어나면 이벤트 진입점을 더 명확히 나눌 필요가 있다.

현재 결론:

- 지금 단계에서는 `USkillComponent`를 그대로 유지하는 것이 맞다.
- 실제 스킬이 붙기 전까지는 "스킬 슬롯 관리자" 역할에 집중시키는 편이 좋다.

### `USkillEffectBase`

현재 역할:

- 실제 스킬 효과 실행 추상 베이스
- 소스 액터, 타겟 액터, 지속시간 입력 수신
- 버프/공격 스킬 타입 구분의 기반 제공

현재 평가는 다음과 같다.

- 스킬 발동 결과를 별도 객체로 분리해 둔 점이 확장에 유리하다.
- `UBuffSkillEffect`, `UOffensiveSkillEffect`로 역할 기반 분기를 미리 나눈 것도 좋다.
- 다만 아직은 공통 컨텍스트가 단순해서, 나중에 범위, 위치, 시전자 편대 슬롯 같은 정보가 필요해질 수 있다.

리팩토링 필요 포인트:

1. 이후 실제 스킬이 붙으면 `FSkillContext` 같은 별도 실행 컨텍스트 구조를 도입하는 것이 좋다.
2. 지금은 UObject 기반 인스턴스 생성으로 충분하지만, 상태가 긴 스킬이 많아지면 실행 수명 관리 방식을 다시 봐야 한다.
3. 버프 적용과 공격 생성이 복잡해지면 별도 보조 컴포넌트나 시스템과의 연결 규칙을 문서화할 필요가 있다.

현재 결론:

- 현 단계에서는 `USkillEffectBase`가 "실행 확장 포인트"로서 적절하다.
- 실제 스킬 구현이 시작되기 전까지는 이 레이어를 더 무겁게 만들 필요는 없다.

### `FSkillSpec`와 `ESkillType`

현재 역할:

- 스킬 식별자와 표시 이름 보관
- 쿨다운과 지속시간 보관
- 효과 클래스 참조 보관
- 버프/공격 타입 구분

현재 평가는 다음과 같다.

- 현재 로드아웃에 넣기 좋은 최소 단위 데이터 구조다.
- 단순한 구조라 BP에서 다루기도 쉽다.
- 다만 스킬 수가 늘어나면 지금의 평면 필드만으로는 사거리, 비용, 이펙트 키 같은 파생 정보가 부족할 수 있다.

리팩토링 필요 포인트:

1. 실제 스킬 구현이 시작되면 `Range`, `Cost`, `TargetPolicy` 같은 필드가 필요할 수 있다.
2. 장기적으로는 `FSkillSpec`를 DataAsset 참조 구조로 줄이는 방향도 고려할 수 있다.
3. 스킬 타입 enum은 현재 충분하지만, 나중에 `Utility`, `Summon`, `Interrupt` 같은 전투 역할이 생기면 확장 후보가 된다.

현재 결론:

- 지금은 `FSkillSpec`를 로드아웃 내장 데이터로 유지하는 것이 가장 단순하다.
- 실제 콘텐츠 양이 커지면 그때 외부 자산화하는 것이 자연스럽다.

### 이번 정리 반영 사항

- `USkillComponent` 내부에서 스킬 스펙 타입/쿨다운/지속시간을 적용 시점에 한 번 더 보정
- 스킬 발동 시 소유자와 쿨다운 값을 한 번 더 안전하게 확인

### 현재 계층 결론

스킬 계층은 현재 다음처럼 보는 것이 가장 명확하다.

- `FSkillSpec`
  - 어떤 스킬을 쓸지 설명하는 데이터
- `USkillComponent`
  - 어떤 슬롯이 준비되어 있고 지금 쓸 수 있는지 관리
- `USkillEffectBase`
  - 실제로 무슨 일이 일어나는지 실행

즉 스킬도 로드아웃과 같은 방향으로, 데이터와 실행을 분리한 구조를 이미 갖추고 있다.

## 5차 정리: 레거시 정리와 남은 기술부채

### 범위

이번 정리 대상:

- `UHomingMovementComponent`
- `UEnemyManager`
- `ABulletBase` 잔여 레거시 흔적

### `UHomingMovementComponent`

현재 역할:

- 탄환 소유자의 현재 타겟을 기준으로 회전 보간
- 직진 이동 적용

현재 평가는 다음과 같다.

- 현재 프로젝트에서는 기본 발사체가 유도를 적극 사용하지 않기 때문에 보조 성격의 컴포넌트가 되었다.
- 그렇더라도 기존 BP나 특수 탄환에서 재사용될 가능성은 있어 유지 가치는 있다.
- 다만 이전 구현에는 `IsPendingKill()` 사용과 불필요한 흔적이 남아 있었다.

정리 방향:

- 소유자와 타겟 유효성 검사를 `IsValid()` 기반으로 정리
- 오래된 경고를 제거
- 현재 역할을 "옵션형 보조 이동 컴포넌트"로 간주

### `UEnemyManager`

현재 역할:

- 현재 월드의 적 Pawn 목록 보관
- 적 추가
- 파괴 시 목록 정리

현재 평가는 다음과 같다.

- 락온과 자동 사격의 공통 데이터 원천으로서 단순하고 유용하다.
- 다만 중복 등록 방지와 포인터 안정성을 조금 더 챙기는 편이 좋다.

정리 방향:

- 중복 등록 방지
- 배열을 `TObjectPtr` 기반으로 보관
- 리스트 반환은 참조 유지

### `ABulletBase` 잔여 레거시

현재 역할 자체는 이미 정리되었지만, 헤더에는 아직 오래된 흔적이 일부 남아 있었다.

정리 방향:

- 깨진 주석 제거
- 사용하지 않는 전방 선언 제거
- 기본 이동값을 헤더 기본값으로 명시
- 포인터를 `TObjectPtr`로 맞춰 현재 프로젝트 스타일과 정합성 유지

### 이번 정리 반영 사항

- `UHomingMovementComponent`의 `IsPendingKill()` 경고 제거
- `UHomingMovementComponent`의 빈 `BeginPlay()` 제거
- `UEnemyManager`의 적 등록 중복 방지 및 보관 타입 정리
- `ABulletBase` 헤더의 오래된 흔적과 포인터 표기 정리

## 현재 남은 기술부채

현재 기준으로 코드 정리 관점에서 남아 있는 항목은 많지 않다.

1. `GetEnemys()` 이름
- 오탈자 성격이 있어 장기적으로는 `GetEnemies()`로 정리하는 편이 좋다.
- 다만 현재 참조 지점이 있어, 이름 변경은 기능 작업과 분리해서 안전하게 하는 것이 좋다.

2. `ABulletBase`의 유도 타겟 인터페이스
- 지금은 거의 쓰이지 않지만 `HomingMovementComponent`와 연결점으로 남아 있다.
- 특수 탄환 기획이 정해지면 유지/삭제를 결정하는 편이 좋다.

3. `CraftLoadout`와 전투 타입 정의의 결합
- 공격 타입/패턴/로드아웃 구조체 정의를 공용 타입 헤더로 분리할 여지가 있다.

4. `AP_Player`의 조정자 책임
- 발사 판단은 많이 빠졌지만, 카메라와 편대 갱신 책임은 여전히 크다.
- 기능 확장이 더 진행되면 이 부분이 다시 가장 큰 확장 포인트가 된다.

## 이후 권장 순서

정리 작업을 닫고 다시 기능 작업으로 돌아간다면 다음 순서가 가장 자연스럽다.

1. 타겟 우선순위와 보스 약점 시스템
2. 보스 페이즈와 저지 패턴 구조
3. 레일 구간/기믹 이벤트
4. 생존 위험물과 궤도 압박
5. 실제 스킬 구현

즉 현재 코드베이스는 "기체/발사/로드아웃/스킬 골격"까지는 정리된 상태이고,
이후부터는 전투 콘텐츠 계층을 붙여 나가는 단계라고 보는 것이 맞다.
