# 남은 구현 슬라이스 정리

## 목적

이 문서는 스플라인 체이스 슈팅 프로토타입의 남은 작업을 정리해, 다음 작업 때 구조를 다시 파악하지 않고 바로 이어서 구현할 수 있도록 만든 기록입니다.

앞으로의 작업 원칙은 계속 동일합니다.

- 현재 `AActor`, `APawn` 클래스 계층 구조는 유지합니다.
- 상속을 늘리기보다 기능별 `UActorComponent`를 추가하는 Has-a 구조를 우선합니다.
- 컴포넌트끼리 직접 강하게 의존하지 않고, 소유 액터, 인터페이스, 델리게이트를 통해 연결합니다.
- 언리얼 네이밍, `UPROPERTY` 카테고리, Blueprint 노출 범위를 의도적으로 관리합니다.

## 현재 구현된 기반

### 레일 이동

구현된 요소:

- `UPathFollowerComponent`
- `URailOffsetComponent`
- `AP_Player`의 레일 이동 조합 로직

동작 방식:

1. `UPathFollowerComponent`가 지정된 스플라인을 따라 전진하며 기본 월드 트랜스폼을 계산합니다.
2. `AP_Player`에서는 PathFollower가 직접 Owner 위치를 바꾸지 않도록 설정합니다.
3. `URailOffsetComponent`는 좌우/상하 입력을 받고, 로컬 이격값을 제한하며, 원위치 복귀와 시각적 기울기를 계산합니다.
4. `AP_Player`가 스플라인 기본 트랜스폼과 로컬 레일 이격값을 합쳐 최종 Pawn 위치를 만듭니다.
5. 기체 비주얼은 이동 방향에 따라 기울지만, 카메라는 메쉬 기울기에 과하게 끌려가지 않도록 더 부드럽게 유지됩니다.

현재 결과:

- 플레이어는 스플라인을 따라 자동 전진합니다.
- 플레이어는 레일 기준으로 위, 아래, 왼쪽, 오른쪽 회피 이동을 할 수 있습니다.
- 기체 메쉬는 자연스럽게 피치/롤 기울기가 들어가고, 카메라는 과도하게 흔들리지 않습니다.

### 편대와 스왑

구현된 요소:

- `USquadComponent`
- `ASquadCraftActor`
- `AP_Player`의 편대 스폰 및 갱신 흐름

동작 방식:

1. `AP_Player`는 계속 플레이어가 조종하는 루트 Pawn 역할을 유지합니다.
2. `AP_Player`가 왼쪽, 센터, 오른쪽 `ASquadCraftActor` 3기를 스폰합니다.
3. `USquadComponent`는 현재 활성 슬롯과 편대 오프셋을 관리합니다.
4. 왼쪽/오른쪽 기체는 센터보다 살짝 뒤와 아래에 배치되어 V자에 가까운 편대를 만듭니다.
5. `SwapLeft`, `SwapRight` 입력은 편대 위치를 바꾸는 것이 아니라 현재 조종 주체 슬롯을 바꿉니다.
6. 활성 기체는 플레이어 직접 발사를 담당합니다.
7. 비활성 기체는 자동 지원 사격을 수행할 수 있습니다.

현재 결과:

- 편대 위치는 안정적으로 유지됩니다.
- 스왑은 물리적 위치 교체가 아니라, 현재 조종하는 기체 슬롯 변경으로 동작합니다.
- 이후 기체별 스탯, 스킬, 무기 개성을 추가하기 좋은 구조가 되었습니다.

### 기체 공격

구현된 요소:

- `UCraftAttackComponent`
- `ECraftAttackPattern`
- `ASquadCraftActor::FireAt`
- `ASquadCraftActor::TryAutoFireAt`

동작 방식:

1. 각 기체는 자기만의 `UCraftAttackComponent`를 가집니다.
2. `ProjectileClass`는 해당 기체가 발사할 총알 Blueprint 또는 C++ 총알 클래스를 지정합니다.
3. `AttackPattern`으로 발사 방식을 선택합니다.
4. `Single`은 목표 지점을 향해 한 발을 발사합니다.
5. `Burst`는 같은 방향으로 여러 발을 발사하며, 시작 위치를 좌우로 살짝 벌립니다.
6. `Spread`는 `SpreadAngle` 범위 안에서 여러 발을 부채꼴로 퍼뜨려 발사합니다.
7. `AutoFireInterval`은 지원 기체의 자동 발사 간격을 조절합니다.
8. `MultiShotSpacing`은 여러 발이 완전히 같은 위치에 스폰되는 것을 방지합니다.

현재 결과:

- 센터, 왼쪽, 오른쪽 기체가 서로 다른 총알 클래스와 공격 패턴을 가질 수 있습니다.
- `Single`, `Burst`, `Spread`를 Blueprint에서 기체별로 조정할 수 있습니다.
- 기존의 플레이어 한 곳 중심 발사 구조는 제거하고, 기체별 공격 컴포넌트 구조로 정리했습니다.

### 총알과 데미지

구현된 요소:

- `ABulletBase::ProcessImpact`
- `ABulletBase::Damage`
- 유도탄 타겟 무효화 처리

동작 방식:

1. 총알은 Hit와 Overlap 모두 `ProcessImpact`를 통해 처리합니다.
2. 맞은 액터에 `UStatComponent`가 있으면 총알 데미지를 적용합니다.
3. 총알은 자신을 발사한 Owner를 무시합니다.
4. 총알은 안전장치로 다른 `ABulletBase` 액터도 무시합니다.
5. 유도탄은 타겟이 사라지거나 죽으면 타겟을 비우고, 이상하게 회전하지 않고 앞으로 계속 날아갑니다.

현재 결과:

- 기본 총알 데미지가 실제 스탯 시스템과 연결되었습니다.
- 유도탄은 타겟이 사라졌을 때 더 자연스럽게 동작합니다.
- 총알끼리 충돌하지 않도록 프로젝트 콜리전 설정과 코드 안전장치가 함께 적용되어 있습니다.

## 남은 슬라이스 1: 기체 정체성과 로드아웃

목표:

각 기체를 단순히 메쉬와 무기 설정만 다른 객체가 아니라, 실제 gameplay unit으로 만듭니다.

추천 추가 요소:

- `UCraftLoadoutComponent`
- 선택 사항: `FCraftLoadoutData` 구조체
- 선택 사항: `UCraftAbilityComponent`

책임:

- 기체 이름, 역할, 총알 클래스, 공격 패턴, 데미지 보정, 쿨타임 보정, 스킬 참조를 저장합니다.
- 기체별 튜닝 값을 한 곳에서 관리합니다.
- `ASquadCraftActor`가 로드아웃 데이터를 `UCraftAttackComponent`에 적용하도록 합니다.
- 이후 스킬 시스템을 추가할 때 `ASquadCraftActor`가 비대해지는 것을 막습니다.

추천 구현 순서:

1. 역할, 총알 클래스, 공격 패턴, 튜닝 값을 담는 `FCraftLoadoutData`를 추가합니다.
2. `ASquadCraftActor`에 `UCraftLoadoutComponent`를 추가합니다.
3. `ApplyLoadoutToAttackComponent` 같은 적용 함수를 만듭니다.
4. 로드아웃 설정을 Blueprint에서 편집 가능하게 노출합니다.
5. 시간이 지나며 Blueprint 곳곳에 흩어진 기체별 전투 튜닝을 로드아웃으로 옮깁니다.

이 작업이 중요한 이유:

- 기체 스왑이 실제 gameplay 의미를 갖게 됩니다.
- 기체마다 다른 스킬과 무기 성향을 줄 수 있습니다.
- 보스 저지 패턴에서 특정 역할 기체가 필요하도록 확장할 수 있습니다.

## 남은 슬라이스 2: 플레이어 조준 발사와 지원 사격 분리

목표:

플레이어가 직접 조준하는 발사와 서포트 기체의 AI 자동 사격을 명확히 분리합니다.

추천 추가 요소:

- `UPlayerAimFireComponent`
- `USupportFireComponent`
- 선택 사항: `IAimTargetProvider` 인터페이스

책임:

- `UPlayerAimFireComponent`는 마우스, 카메라, 락온 정보를 이용해 플레이어 조준 지점을 계산합니다.
- `USupportFireComponent`는 비활성 기체가 언제, 어떤 타겟을 향해 발사할지 결정합니다.
- `UCraftAttackComponent`는 계속 저수준 총알 스폰 실행자 역할만 유지합니다.

추천 구현 순서:

1. 목표 지점과 타겟 액터를 반환하는 조준 제공 인터페이스 또는 컴포넌트를 추가합니다.
2. 활성 기체의 발사는 `UPlayerAimFireComponent`를 통해 라우팅합니다.
3. 비활성 기체 자동 발사 타이밍과 타겟 선택을 `USupportFireComponent`로 이동합니다.
4. `AP_Player`는 전체 흐름을 연결하는 조정자 역할만 유지합니다.
5. 이후 타겟 우선순위 규칙을 추가합니다.

이 작업이 중요한 이유:

- 메인 기체는 플레이어가 원하는 지점을 정확히 조준할 수 있습니다.
- 서포트 기체는 보스 약점, 가까운 적, 위험도가 높은 타겟을 자동으로 우선할 수 있습니다.
- 공격 로직을 플레이어, 적, 보스 모두에서 재사용하기 쉬워집니다.

## 남은 슬라이스 3: 타겟 우선순위와 보스 약점

목표:

락온과 자동 사격이 보스 약점, 저지 마커, 전술적 타겟을 이해하도록 만듭니다.

추천 추가 요소:

- `UTargetableComponent`
- `UTargetPriorityComponent`
- `UBossWeakPointComponent`

책임:

- 액터 또는 컴포넌트를 타겟 가능 대상으로 표시합니다.
- 타겟 타입을 일반 적, 보스 코어, 약점, 저지 마커, 위험물 등으로 구분합니다.
- 타겟 우선순위와 유효 시간대를 노출합니다.
- 지원 사격과 락온이 노출된 약점이나 필수 마커를 우선하도록 만듭니다.

추천 구현 순서:

1. 타겟 타입과 우선순위를 가진 `UTargetableComponent`를 추가합니다.
2. `ULockOnComponent`가 타겟 가능 객체를 우선하도록 갱신합니다.
3. 약점을 노출하거나 숨기는 `UBossWeakPointComponent`를 추가합니다.
4. 지원 사격이 단순 적 타겟이 아니라 타겟 우선순위를 기준으로 대상을 고르도록 바꿉니다.

이 작업이 중요한 이유:

- 보스전에는 약점 노출 시간이 필요합니다.
- 저지 패턴에는 순서대로 파괴해야 하는 마커가 필요합니다.
- 자동 사격이 레이드 핵심 타겟이 아닌 낮은 우선순위 적에게 낭비되는 것을 막을 수 있습니다.

## 남은 슬라이스 4: 보스 페이즈와 패턴 상태

목표:

일반 적 Pawn을 과하게 복잡하게 만들지 않고, 보스 레이드 구조를 추가합니다.

추천 추가 요소:

- `UBossPhaseComponent`
- `UBossPatternComponent`
- `UInterruptSequenceComponent`

책임:

- 현재 보스 페이즈를 추적합니다.
- HP 기준, 시간 기준, 스크립트 트리거 기준으로 페이즈를 전환합니다.
- 델리게이트를 통해 보스 패턴 시작과 종료를 알립니다.
- 저지 성공/실패 상태를 추적합니다.
- 실패 시 스턴, 큰 데미지, 레일 위험 같은 결과를 발생시킵니다.

추천 구현 순서:

1. 페이즈 인덱스와 페이즈 변경 델리게이트를 가진 `UBossPhaseComponent`를 추가합니다.
2. `UStatComponent`의 HP 기준으로 간단한 페이즈 전환을 만듭니다.
3. 패턴 시작/종료 이벤트를 가진 `UBossPatternComponent`를 추가합니다.
4. 순차 마커 타격을 관리하는 `UInterruptSequenceComponent`를 추가합니다.
5. 보스 약점 노출을 패턴 윈도우와 연결합니다.

이 작업이 중요한 이유:

- 일반 적 구조를 유지하면서 보스만 레이드형으로 확장할 수 있습니다.
- 광역기, 즉사기, 저지 패턴 같은 보스전 핵심을 구현할 수 있습니다.
- 보스 로직을 모듈화해 재사용하기 쉬워집니다.

## 남은 슬라이스 5: 레일 구간과 기믹 이벤트

목표:

스플라인 경로가 추격, 생존, 요격 같은 레벨 디자인 구간을 직접 구동하도록 만듭니다.

추천 추가 요소:

- `URailSectionListenerComponent`
- `UGimmickSpeedModifierComponent`
- `ASplinePathManager` 확장

책임:

- 스플라인 거리 또는 이름 있는 마커를 기준으로 레일 구간을 정의합니다.
- 구간 진입/이탈 이벤트를 브로드캐스트합니다.
- 속도 변화, 부스트 게이트, 감속 구역, 추격 거리 압축 등을 적용합니다.
- 차선 봉쇄, 벽, 궤도 파괴, 앵커 포인트 같은 위험 요소를 트리거합니다.

추천 구현 순서:

1. `ASplinePathManager`에 구간 메타데이터를 추가합니다.
2. 구간 변경 델리게이트를 추가합니다.
3. 플레이어와 보스 액터에 `URailSectionListenerComponent`를 추가합니다.
4. `UPathFollowerComponent` 또는 별도 속도 컴포넌트에 속도 보정 스택을 추가합니다.
5. 첫 번째 간단한 기믹으로 부스트 게이트 또는 감속 구역을 만듭니다.

이 작업이 중요한 이유:

- 프로토타입이 초기 기획의 스플라인 추격 슈팅에 더 가까워집니다.
- 보스 행동과 플레이어 속도가 맵 구간에 반응할 수 있습니다.
- 레벨 디자인 이벤트를 플레이어 Pawn에 하드코딩하지 않고 경로/구간 데이터로 관리할 수 있습니다.

## 남은 슬라이스 6: 생존 위험 요소와 레일 압박

목표:

레일 이격 이동과 기체 스왑이 실제로 중요해지는 공격 패턴을 추가합니다.

추천 추가 요소:

- `URailHazardComponent`
- 벽, 레이저, 경고 마커, 궤도 점유 공격용 Hazard 액터

책임:

- 스플라인 위치와 로컬 레일 오프셋 공간을 기준으로 위험물을 스폰합니다.
- 실제 위험이 활성화되기 전에 경고 표시를 보여줍니다.
- 플레이어의 이동, 포지셔닝, 기체 스왑을 강제합니다.
- 이후 특정 기체 슬롯만 데미지를 받는 구조로 확장할 수 있습니다.

추천 구현 순서:

1. 로컬 레일 공간 기준의 Hazard 볼륨을 정의합니다.
2. 간단한 경고 마커를 스폰합니다.
3. 지연 시간 후 충돌을 활성화합니다.
4. `UStatComponent`를 통해 데미지를 적용합니다.
5. 이후 보스 패턴과 레일 구간 이벤트에 연결합니다.

이 작업이 중요한 이유:

- 레일 이격 이동이 단순 자유 이동이 아니라 생존 판단 요소가 됩니다.
- 플레이어는 X/Y 회피와 편대 상태를 함께 신경 써야 합니다.
- 보스 패턴에 공간 압박이 생깁니다.

## 다음에 이어서 할 추천 작업

다음에 개발을 이어간다면 가장 좋은 시작점은 다음 순서입니다.

1. `UCraftLoadoutComponent`를 구현합니다.
2. 기체별 공격 튜닝을 로드아웃 데이터로 옮깁니다.
3. 쿨타임 필드나 스킬 클래스 참조 정도의 간단한 스킬 자리만 먼저 만들어둡니다.

이 흐름이 현재 구현된 편대 공격 시스템에서 기체별 개성, 스킬, 보스 저지 규칙으로 넘어가기 가장 자연스러운 연결 지점입니다.
